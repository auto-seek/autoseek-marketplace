# 项目交付团队

适合小型产品迭代、流程自动化、数据整理和项目方案评审。团队成员以职业职责协作，不预设虚构个人身份或生活背景。

| 成员       | 工作方式                           | 主要交付                         |
| ---------- | ---------------------------------- | -------------------------------- |
| 项目负责人 | 重结果与优先级，明确范围，整合结果 | 简短计划、任务安排、最终交付说明 |
| 产品分析师 | 善于提问，重证据与用户价值         | 需求说明、验收条件、方案比较     |
| 工程师     | 务实、优先复用，先做最小可验证改动 | 代码、脚本、运行说明与检查结果   |
| 质量审查员 | 审慎具体，关注实际缺陷             | 验收结果、问题证据和未检查项     |

项目负责人在团队根层；其他三名成员位于“交付协作”部门。根群包含全部四人，部门群包含三名交付成员。它们就是执行工作任务的同一批成员。

## 从一个实际任务开始

创建团队后，把下面这类任务发给项目负责人（将路径换成自己的文件）：

> 根据项目里的 requirements.md，把现有 CSV 清洗脚本改成命令行工具。先确认输入输出与错误处理要求，再实现并用项目现有样例验证。交付可运行脚本、使用说明和检查结果；保留原始数据，不发布到外部。

如果还没有项目，也可以从一个文档任务开始：

> 根据这份会议纪要整理本周交付计划，列出目标、负责人、依赖和验收条件。未确定的事项标为待确认，不编造截止日期。

需要群内讨论时，使用 @ 选择具体成员：

> @产品分析师 @质量审查员 请基于 requirements.md 核对验收条件，指出会影响实现的缺口。每人给出自己的结论和依据，有具体问题再继续讨论。

小任务可由负责人直接完成；无需每次召集所有人，也无需走固定评审链。没有新信息时成员结束本轮，避免反复互相 @。

## 使用与定制

在市场安装后 fork，再用个人副本创建团队。可调整岗位职责、部门结构和用户的模型配置；本包不绑定模型、凭据或权限模式，不需要角色卡、媒体资源或额外应用。交付检查技能可选装。

各岗位按实际文件和工具结果报告完成情况，未执行的检查会明确标注。模板描述的是期望工作方式，重要交付仍应核对实际结果。
